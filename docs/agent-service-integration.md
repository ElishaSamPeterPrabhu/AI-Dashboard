# Agent Service Integration

## Overview

Every AI node on the canvas is backed by a Trimble Agent managed through the Agent Service API (`https://api.trimble.com/v1` or the platform base URL). This document specifies exactly how the dashboard uses each resource group.

---

## Authentication

All requests carry a TID access token in the `Authorization: Bearer <token>` header. Token acquisition follows the same PKCE flow as `ModusAssistant.tsx` (see `auth-and-security.md`).

Required scopes: `openid agents`

The JWT must carry an `account_id` claim. If absent, the Agent Service returns errors on most write operations. The dashboard detects this on first load and shows:
```
[Modus Alert] Your Trimble account is not configured.
Go to My Profile → select a default account → return here.
[Open My Profile ↗]
```

## Agents Resource Group

### Listing agents (Bind-existing picker)

```
GET /v1/agents
  ?filter=<FIQL>&pageSize=20&skipToken=<cursor>&fields=id,name,description,icon,models
```

**Common FIQL filters for the picker:**
```
# Agents I admin
filter=admins==(users:{myTidUserId})

# Agents I can use (any role)
filter=actors==(users:{myTidUserId})

# Search by name (fuzzy — use autocomplete endpoint instead for live search)
filter=name=={searchTerm}

# Agents I own, updated recently
filter=admins==(users:{myTidUserId});updatedAt=ge=2025-01-01T00:00:00Z
```

**Autocomplete (as-you-type in picker):**
```
GET /v1/search/autocomplete?q={userInput}&types=agents&pageSize=10
```

Use autocomplete for real-time search. Full search (`GET /v1/search`) for rich results when the user pauses.

### Creating an agent (Auto-provision flow)

```
POST /v1/agents
Content-Type: application/json

{
  "name": "{workflowName} — {nodeLabel}",
  "description": "{user-authored description}",
  "instructions": "{LLM-generated instructions from description}",
  "models": [{ "id": "gemini-2.5-flash", "provider": "google" }],
  "acl": {
    "admins": ["users:{creatorTidId}"],
    "users": ["users:{creatorTidId}"]
  },
  "quota": {
    "promptLimit": 100,
    "tokenLimit": 100000,
    "trackingPeriodMinutes": 1440
  }
}
```

**Response:** use the returned `id` as `agentBinding.agentId`. Do NOT immediately call `GET /agents/{id}` — reads are eventually consistent. Trust the POST response body.

**Tools and knowledge libraries are added in a separate PATCH step** (see Agent Configurations below).

### Updating an existing agent's config

When the user edits an AI node's description, connected MCPs, or connected Knowledge nodes:

```
PATCH /v1/agents/{agentId}/configs
{
  "instructions": "{updated instructions}",
  "tools": [{
    "type": "mcp",
    "name": "{toolLabel}",
    "mcpServerUrl": "{mcpServerUrl}",
    "auth": { "type": "actorToken", "scopes": "openid connect" },
    "timeoutSeconds": 900
  }],
  "knowledgeLibraries": [{ "id": "{libraryId}" }]
}
```

Store the returned `configId` on `agentBinding.configId`.

### Deleting an agent

When an AI node is deleted from the canvas (and `agentBinding.mode === "provisioned"`):
- **Soft delete** by default: `DELETE /v1/agents/{agentId}` (reversible; threads preserved)
- **Hard delete** only if the user explicitly requests cleanup: adds `?hard=true` — threads wiped immediately

## Agent Configurations Resource Group

Configurations are versioned. Each PATCH creates a new config version. The current "draft" config is `configs.draft`. The "live" config for end users is the one pointed to by the `production` alias.

```
GET /v1/agents/{agentId}?fields=configs,alias
```

Returns:
```json
{
  "configs": {
    "draft": { "id": "cfg_abc", "version": 3 },
    "latest": { "id": "cfg_abc", "version": 3 }
  },
  "alias": { "production": { "configId": "cfg_xyz", "version": 2 } }
}
```

The dashboard stores `agentBinding.configId = configs.draft.id` after every PATCH. Workflow runs use `configId` from the binding — this pins runs to a specific version so old workflow run artifacts remain reproducible.

---

## Agent Aliases Resource Group

Publishing a config version for end users (promoting draft → production):

```
PATCH /v1/agents/{agentId}/aliases/production
{ "configId": "{configId}" }
```

The AI node panel shows a **"Promote to production"** button when `configs.draft.id !== alias.production.configId`. In practice, the dashboard auto-promotes after every save so draft = production for dashboard-managed agents.

## Threads Resource Group

One thread is created per AI node per workflow run. Thread titles are auto-generated by the Agent Service from the initial prompt.

```
POST /v1/agents/{agentId}/threads
{
  "title": "{workflowName} / {nodeLabel} — {isoTimestamp}"
}
```

**Why threads per node, not one thread per run?**
Each thread holds the conversation history for one agent. Different AI nodes in the same workflow are different agents and must have separate threads. The simulation engine tracks the mapping `{ runId, nodeId } → threadId`.

Thread history is browsable in Trimble Assist — users can continue the conversation from where the simulation left off.

## Executions (Runs) Resource Group

### Starting a run

```
POST /v1/threads/{threadId}/runs
Content-Type: application/json
Accept: text/event-stream

{
  "message": "{user prompt or workflow-generated prompt for this node}",
  "context": [
    { "description": "teamSize", "value": "5" },
    { "description": "velocityStoryPoints", "value": "32" }
  ],
  "model": "gemini-2.5-flash"   // optional override
}
```

The response is an SSE stream of AG UI events. The backend simulation engine consumes this stream and forwards events to the frontend over WebSocket.

### Key AG UI events consumed

| Event type | What we do with it |
|---|---|
| `TEXT_MESSAGE_CONTENT` | Forward as `node:progress` to canvas (streaming text in the trace) |
| `TOOL_CALL_START` | Emit `tool:call` → animate corresponding MCP/Knowledge edge |
| `TOOL_CALL_RESULT` | Emit `tool:result` → deactivate edge animation |
| `SUBAGENT_TEXT_MESSAGE_CONTENT` | Emit `node:progress` on the **child** AI node (identified from the event's `value.agentId`) |
| `RUN_FINISHED` | Parse final message against node's `outputSchema`; emit `node:value` + `node:end` |
| `RUN_ERROR` | Emit `node:error` with error message |

## Tools Resource Group

### Listing built-in tools

Called once on app init, cached for the session:

```
GET /v1/tools
```

Returns the current list of built-in tools (`datetime`, `myprofile`, `user_directory`, `tekla_help`, `trimble_help`, `web_search`). The dashboard populates the "Trimble Built-Ins" section of the node palette from this response — drag any built-in onto an AI node to enable it.

## Search and Batch Resource Group

### Batch loading a workflow with many AI nodes

On workflow load, collecting all agent metadata in one round-trip:

```
POST /v1/batch-get
{
  "requests": [
    { "type": "agent", "id": "agent_abc" },
    { "type": "agent", "id": "agent_def" },
    ...
  ]
}
```

Max recommended batch size: 50. For larger workflows, issue multiple batch-get calls concurrently.

## Reports Resource Group

Per AI node, show a "usage in last 30 days" sparkline in the node's config panel:

```
GET /v1/agents/{agentId}/reports/runs
  ?from={30DaysAgo}&to={today}&granularity=day
```

Renders as a Recharts sparkline inside the node panel. Also shows current quota usage:

```
GET /v1/agents/{agentId}?fields=usage
```

## Subagent Wiring

When AI node B has AI node A as an upstream dependency (A's output connects to B's input port):

- The simulation engine does NOT just pass A's output as text input to B
- Instead, when configuring B's agent, the dashboard adds A's `agentId` to B's `subagents[]`:

```json
{
  "subagents": [{
    "id": "{agentA.agentId}",
    "configId": "{agentA.binding.configId}",
    "overrides": {
      "name": "{agentALabel}",
      "description": "Upstream estimation agent providing {portName} data"
    }
  }]
}
```

B's agent then decides when to call A as a tool, receives A's output as a tool result, and incorporates it into its own response.

**Constraints enforced at Plan Mode validation:**
- Maximum 3 AI node hops in any path (platform recursion limit)
- No cycles among AI nodes
- AI nodes inside Loop Frames may not use subagent wiring (platform restriction: subagents cannot have local tools; the simulation engine uses client-side tool callbacks for Loop coordination)

## Versioning Strategy

Every workflow run stores a snapshot of each node's `agentBinding.configId`. This means:
- Running the same workflow weeks later always uses the exact same agent config version
- Scenario comparisons are meaningful (same config, different inputs)
- If the user edits the node (bumping config version), old runs are unaffected

The AI node panel shows: `v3 (current)` with a history link that opens past config versions.

## FIQL Filter Cookbook

```
# My agents
admins==(users:me)

# Agents shared with my team (Trimble employees)
users==(trimble-employee:true)

# Recently active agents (updated last 7 days)
updatedAt=ge=2025-01-10T00:00:00Z

# Agents using a specific model
configs.models.id==gemini-2.5-flash

# Agents NOT deleted
state==active   (this is the default, no filter needed)

# Combined: my agents updated this month
admins==(users:me);updatedAt=ge=2025-01-01T00:00:00Z

# Agents I can use OR admin (for any-access picker)
actors==(users:me)
```

Note: `*` in FIQL is treated as a literal character — use the autocomplete endpoint for wildcard-style prefix matching.
